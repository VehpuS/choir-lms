## Context

Today's harness (`tools/browser-session/`) serves the `build-browser-test` export, seeds `localStorage` with a mock library, optionally fakes a Google Drive account (`signed-out` / `expired` / `authorized`), and runs steps through `runScenario`. Playback "needs real audio and is out of scope" per the README, and nothing stops a scenario from silently reaching a real host. The review below proposes what to cover and what to add to the tooling so coverage can grow without touching Drive, sound or the network.

## Decisions

- **Same stack, no new runner.** Keep Playwright + `tsx` scenarios and `runScenario`; do not introduce `@playwright/test` (matches the testing policy: no new runner without a migration request). A scenario is a file `tools/browser-session/<area>-<behavior>.scenario.ts`.
- **Offline by construction.** `openMockLibrarySession` installs a catch-all `context.route('**/*')` that aborts and records any request whose origin is not the local server, then `runScenario` fails the scenario if the record is non-empty. Declared mocks (`drive`, `webFiles`) are routed first, so the guard only sees what a scenario forgot to mock.
- **Real stem plus generated tones.** A real choir stem is committed as `packages/mobile-rehearsal-player/src/test-support/fixtures/audio/choir-stem.m4a` (3.8 s, 48 kHz stereo AAC, 62 KB, recorded against the deployed app; each of its three notes is held). Advantages over a tone: it goes through the real compressed-audio decode path (AAC in an MP4 container, as Drive files usually are), it is voice rather than a clean sine so pitch detection is exercised on realistic input, and it gives a known note progression to assert. Chromium's `canPlayType` reports AAC as playable in the CI browser (checked with the pre-installed build; the CI job installs Playwright's Chromium, so a one-line codec probe in the helper fails fast if that ever changes). Generated tones stay for everything that needs an exact length or a loud, steady signal (loops, markers, seeking, queue timing).
- **Deterministic audio.** `buildToneWav({ seconds, hz })` makes a small PCM WAV in memory; the mock Drive serves it for `files/<id>?alt=media` (with `Range` support so seeking works) and `webFiles` serves it for link tracks. Assertions read position/state from the app's own UI and from `HTMLMediaElement` via `page.evaluate`, with the element's volume at 0 (see the debugging skill: never `muted`). A seekable fixed-length file lets loops, markers and the progress bar be checked without timing sleeps.
- **Fake microphone fed by the stem.** Chromium launches with `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream --use-file-for-fake-audio-capture=<wav>`; Chromium wants WAV there, so a helper transcodes the committed stem to a temp WAV at session start (decoding in Node via `ffmpeg` is avoided: the transcode runs once in the browser with `OfflineAudioContext` and the WAV is written by the test helper, so CI needs no extra binary). Recording and pitch flows then get a real `MediaStream` carrying the stem. Measured offline: E4 from about 0.25 to 0.6 s, C♯4 from about 0.75 to 1.1 s, C4 from about 1.25 to 1.9 s, silence after about 2 s. Because every note is held, the shipped pitch pipeline's segmenter reports E4, C♯4, C4 in order, and the raw frames agree. Pitch assertions tolerate the exact timing (the file loops in the fake device, so the scenario waits for the sequence rather than sleeping).
- **Maximum code engagement.** Scenarios prefer the real path end to end over stubs: real decode, real pitch estimator and segmenter, real recorder and writer, real library parser, real bundle builder. Mocks sit only at the boundary (Drive HTTP, web URLs, microphone device).
- **Fixtures as builders.** Extend `mock-library-fixtures.ts` with small builders (`buildMockLoop`, `buildMockPlaylistWithItems`, `buildMockTag`, `buildMockMarkers`, `buildMockLyrics`, `buildMockComposite`, `buildMockRecording`) so each scenario names only the fields it cares about. Fixture storage keys stay covered by the existing spec that keeps them in step with `@org/audio-library-runtime`; each new builder gets a round-trip spec through the real parser.
- **Locators.** Prefer `getByLabel` / role; add an `accessibilityLabel` to the app only when no stable accessible name exists. Never select by style or test-ids invented just for tests.
- **Failure evidence.** `runScenario` records a Playwright trace per scenario (written to the output dir only on failure) next to `failure.png`, plus the console errors collected during the run; `expectNoConsoleErrors()` is opt-in per step because the app has known baseline warnings (listed in the debugging skill).
- **Speed.** One build, scenarios run sequentially in one process each; a `--scenario=<substring>` filter on `browser-test` so an agent can run one scenario while iterating. Scenarios share the built export and never rebuild.
- **Agent workflow.** A new `browser-test-coverage` skill is the entry point: bug report → reproduce as a failing scenario first → fix → keep the scenario; new user-visible behavior → add or extend a scenario in the same change (new line in the testing policy and `AGENTS.md`).

## CI time

Measured on the first CI run of this change: the `browser` job waited for `main` (about 5m45s) and then took about 3m45s itself (`npm ci` 67 s, Chromium 17 s, the Expo export about 115 s, scenarios the rest), so a pull request waited close to ten minutes in all. Decisions:

- **Run alongside `main`.** The `browser` job has its own install and build, so it no longer waits for `main`; a PR waits for the slower job, not the sum. It has a 15-minute timeout.
- **Scenarios in parallel, all to the end.** `run-scenarios.ts` runs three at a time and does not stop at the first failure, so one failure never hides the rest. The default lane went from about 44 s serial to about 14 s.
- **Opt-in lane for slow or machine-sensitive scenarios.** Anything named `*.matrix.scenario.ts` (device profiles, CPU throttling, sample rates, long tracks, WebKit) runs through `browser-test-matrix`, from the `Browser matrix` workflow: manual dispatch, or the `browser-matrix` PR label. Rule of thumb for a new scenario: more than a few seconds, or needs a quiet CPU, goes in the matrix lane.
- **A reliable instrument.** The first CI run also failed: the "clean tone" check read clicks in the captured audio because the tap used a main-thread script processor, which drops blocks on a loaded machine. The tap now runs on an `AudioWorklet` (audio thread); 0 of 8 runs failed under 12 busy loops, where the old tap failed about 1 in 4.
- **Not done, on purpose.** Caching the Expo export across runs (it rebuilds only when app inputs change, so most test-only PRs would hit it, but Nx's local cache is not persisted between CI runs without extra setup) is left for a follow-up if the build stays the long pole.

## Fixtures (decided)

- Choir stem: committed as above (from the user's Drive link). Its sung notes are E4, then C#4, then C; the pitch scenarios assert exactly that progression.
- Library bundles for backup, restore and import: generated in the scenario with the `audio-library-runtime` bundle builder, so they follow the code's format and upgrade steps rather than a frozen file.
- Score fixtures, **kept full length** so the viewer is not tested only on toy input: the MusicXML (7 parts: Soprano, Mezzo-soprano, Alto, Tenor, Baritone, Bass, Beatbox; 861 measures; 1.6 MB) is committed untrimmed as `.musicxml`, with its compressed `.mxl` form (about 39 KB, which the loader accepts) built from it in the scenario to cover both paths; and the Standard MIDI file (format 1, 7 tracks, 62 KB). Both are the user's own arrangements, so there is no licensing concern. The stem is unrelated to the score, so score-follow and "my parts" scenarios use the score on its own (the stem is not time-aligned to it).
- Long audio: generated tones of several minutes (`buildToneWav({ seconds: 600 })`, served with `Range`) stand in for a long track, so seeking, the progress bar, loops late in a track and waveform extraction are not only tried on a three-second file. They are generated in memory, so nothing large is committed.

## Playback quality at reduced speed, on varied devices

Slowing a track must not make it sound sloppy. The web path uses the SoundTouch AudioWorklet pitch shifter (`web-pitch-shifter.web.ts`) on a Web Audio `AudioContext`. A scenario cannot listen, so it measures the audio the app produces:

- **Tap the output.** An init script wraps `AudioContext` to (a) force a device sample rate and (b) copy what reaches `destination` into a PCM buffer the scenario reads back. Analysis runs in Node over that buffer.
- **Checks at 1x, 0.75x, 0.5x and 0.25x** on the long tone and the stem: pitch stays on the source note within a tolerance in cents (using the `pitch-detection` package, so the same estimator the app ships), loudness stays within a band of the 1x render, there are no clicks (a cap on the largest sample-to-sample jump after smoothing out the signal), no dropouts (no silent run inside a sounding region longer than a few milliseconds), and no clipping. Pitch shift (semitones) is checked the same way: the detected note moves by exactly the requested interval at constant speed.
- **Device matrix**, each a profile applied by the helper: Playwright's device descriptors (a recent iPhone, a mid-range Pixel, an iPad, a desktop window), CPU throttling through the DevTools protocol (1x, 4x and 6x slowdown, to simulate low-end phones, where a worklet that misses its deadline shows up as dropouts), and forced `AudioContext` sample rates (22.05, 44.1, 48 kHz; the source is 16 kHz for the stem and 44.1 kHz for tones, so the resample path is exercised both ways). A quick profile (one phone, one desktop, 1x) runs in the default lane on every PR; the full matrix is a separate opt-in lane (below) so CI time stays bounded.
- **Honest limits.** Emulation changes viewport, touch and CPU speed, not the audio stack: real iOS Safari audio is WebKit's, not Chromium's. Adding WebKit and Firefox to the matrix (Playwright supports both) is proposed as a later step and listed under open questions; native iOS/Android playback is out of scope for the browser suite (it needs `react-native-track-player` on device).
- **Readout versus engine.** Speed scenarios assert both the on-screen speed readout and the media element's `playbackRate` and the shaper's applied tempo, so a UI that shows 0.5x while the engine runs at 1x fails.

## Decisions on the open questions

- **WebKit on demand.** Chromium runs on every PR. WebKit is available through the `browser-test-matrix` target (`--browser=webkit`), installed with `npx playwright install webkit` only when that target runs, and is not part of the default CI job. Scenarios stay browser-neutral: Chromium-only flags (fake microphone device, CPU throttling through the DevTools protocol) sit behind a capability check in the helpers, and a scenario that needs them declares `requires: ['chromium']` so it is skipped, not failed, under WebKit. Revisit adding WebKit to a scheduled CI run once the first on-demand runs show how stable it is.
- **Thresholds from a baseline.** Pitch, click and dropout limits are set from the first measured run (baseline plus a margin) in subtask 2.5, and the measured numbers are written next to the limits in the scenario so a change is visible in review.
- **No Git LFS for the fixtures.** The fixtures total about 1.7 MB, and the MusicXML compresses to about 39 KB in Git's own storage, so they add little to clone size. LFS would add cost for every consumer: CI checkouts need `lfs: true`, the Pages deploy and remote agent sessions need LFS installed and an LFS-capable proxy, a missing pull leaves pointer files that fail the scenarios in confusing ways, and LFS storage and bandwidth are quota-limited. A plain-text `.gitattributes` entry marks the MusicXML as `-diff linguist-generated` so reviews and language stats ignore it. Revisit LFS only if committed fixtures grow past roughly 10 MB in total; a spec checks the fixture directory size against that budget so growth is noticed.
