## 1. Offline audio caching

Moved here on 2026-10-12 from `nocturne-visual-system-and-playback-shaping` (items 8.37 and 8.43), at the user's direction, so that change could be completed and archived. Scope widened by the user from a replay cache to long-term offline playback. Nothing here is scheduled: write the design and spec deltas first.

- [x] 1.1 (was 8.37) **Progress 2026-10-26: (a) in-memory LRU, (b), and (e) are done on web** (`saved-track-audio-cache.ts`, shared in-flight with waiter counting in `saved-track-web-download.ts`, keyed by `driveFileId` + `modifiedTime`, 200 MB budget; downloads without a version are never reused). **(c) done 2026-10-27: the waveform prefetch downloads through the shared download (cache hit or joins the player's), opting out of reset cancellation.** **(a) persistence done 2026-10-27 on web: `playback/audio-cache/` (an `AudioStore` interface, an IndexedDB store, a versioned LRU over it; native uses a no-op store until 1.4); a reload reads the persisted file inside the shared download. (user, 2026-09-30): no. On web every `add()` fetches the whole Drive `alt=media` response into a fresh blob (`saved-track-web-download.ts`), and the next `reset()` / `stop()` revokes it (`saved-track-player-web-load.ts`). Measured in the preview on 2026-09-30: each press of `Preview` in the loop builder, a new range (a new `loop-preview:<source>:<start>:<end>` item id), a track or loop of the same file, and every 8.35 reload is a full download of the same 3.4–8 MB (2–28 s depending on the connection). Plan: (a) a size-capped LRU of downloaded blobs keyed by `driveFileId` + Drive content version (`modifiedTime`, matching 4.2's peak cache key), kept in memory and optionally in Cache Storage or IndexedDB so a reload is warm, with `reset()` releasing the player's hold rather than revoking a cached blob; (b) concurrent requests for one file share one in-flight download; (c) 4.1's decode for waveform peaks reads the same cached bytes instead of fetching again; (d) check what react-native-track-player does natively (it streams the URL with headers, so repeated starts may already re-buffer) before deciding whether the cache is web-only; (e) cover key/version invalidation, LRU eviction, the shared in-flight download, and abort-on-supersede (8.33: a superseded request must not cancel a download another waiter still needs) in `saved-track-web-download.spec.ts`.

- [x] 1.11 **Offline playback without a Drive session** (found while planning 1.6; spec requirement). A cached track, loop or adjusted item plays with no network or session, and an uncached file offline says it needs a connection instead of showing a playback error. Needs a check of what the play path needs from Drive (metadata, auth) before the cached bytes can be served. **Checked 2026-10-27: metadata is local (a source's availability, `modifiedTime` and duration come from the saved library), and `startSavedTrackDownload` already reads the persisted copy before it fetches, so only auth gates playback: `createSavedTrackPlaybackPreconditionIssue` and the token checks in `runtime-core.ts`, `runtime-commands.ts` and `marker-jump-command.ts`; and on web a track with no token has empty headers, which `patchSavedTrackPlayerWebTrack` treats as a plain URL, so the player would get the raw Drive URL. Decisions (user, 2026-10-27): a stored copy is used when there is no session or the browser reports offline, even while signed in; an uncached file with no session while online keeps `Google Drive access required`, and while offline says `This file needs a connection`. Plan (web only; native follows in `native-playback-follow-ups`): (1) `isDeviceOffline()` from `navigator.onLine`; (2) the playback request takes a nullable token, and with none (or offline) builds a `storedOnly` track with no auth header; (3) the web load patch serves a `storedOnly` track from the in-memory then persisted copy only, and throws a `StoredCopyUnavailableError` (offline or not) on a miss; (4) the precondition no longer blocks an unauthorized item where offline storage exists, and the three load sites pass a null token instead of bailing; (5) the runtime issue maps that error to `Needs a connection` (offline) or the reconnect issue (online); (6) specs for the request, the web load, the precondition and the issue, then a browser check with the session cleared and a kept file. **Done 2026-10-27, web only: `canPlayStoredCopies` (true on web) lets the precondition pass without a session; `resolveStoredOnly` makes the request `storedOnly` with no token or while `navigator.onLine` is false; the web load serves such a track from `readStoredSavedTrackBlob` (memory, then the stored copy at the library's `modifiedTime`) and otherwise throws `StoredCopyUnavailableError`, which the runtime issue maps to `Needs a connection` (offline) or `Google Drive access required` (online, no session). Verified in the browser preview by seeding a kept entry and faking `navigator.onLine = false`: the file played from the stored copy with no network request, and after deleting the entry the same play showed the `Needs a connection` card. Not exercised: a real expired session (the fake offline flag covered the stored-only path; the no-token branch is covered by specs only), duration hydration and waveform prefetch without a session (both still need a token and skip), and a signed-in player that loses the network mid-play.**
