## 1. Offline audio caching

Moved here on 2026-10-12 from `nocturne-visual-system-and-playback-shaping` (items 8.37 and 8.43), at the user's direction, so that change could be completed and archived. Scope widened by the user from a replay cache to long-term offline playback. Nothing here is scheduled: write the design and spec deltas first.

- [ ] 1.1 (was 8.37) **Progress 2026-10-26: (a) in-memory LRU, (b), and (e) are done on web** (`saved-track-audio-cache.ts`, shared in-flight with waiter counting in `saved-track-web-download.ts`, keyed by `driveFileId` + `modifiedTime`, 200 MB budget; downloads without a version are never reused). **(c) done 2026-10-27: the waveform prefetch downloads through the shared download (cache hit or joins the player's), opting out of reset cancellation.** **Left: (a) persistence behind a store interface, (d) native check.** **Playing the same file again always downloads it again; there is no cache (improvement).** Answers "isn't it already in cache?" (user, 2026-09-30): no. On web every `add()` fetches the whole Drive `alt=media` response into a fresh blob (`saved-track-web-download.ts`), and the next `reset()` / `stop()` revokes it (`saved-track-player-web-load.ts`). Measured in the preview on 2026-09-30: each press of `Preview` in the loop builder, a new range (a new `loop-preview:<source>:<start>:<end>` item id), a track or loop of the same file, and every 8.35 reload is a full download of the same 3.4–8 MB (2–28 s depending on the connection). Plan: (a) a size-capped LRU of downloaded blobs keyed by `driveFileId` + Drive content version (`modifiedTime`, matching 4.2's peak cache key), kept in memory and optionally in Cache Storage or IndexedDB so a reload is warm, with `reset()` releasing the player's hold rather than revoking a cached blob; (b) concurrent requests for one file share one in-flight download; (c) 4.1's decode for waveform peaks reads the same cached bytes instead of fetching again; (d) check what react-native-track-player does natively (it streams the URL with headers, so repeated starts may already re-buffer) before deciding whether the cache is web-only; (e) cover key/version invalidation, LRU eviction, the shared in-flight download, and abort-on-supersede (8.33: a superseded request must not cancel a download another waiter still needs) in `saved-track-web-download.spec.ts`.
- [ ] 1.2 (was 8.43) **Files that were never played have no waveform.** Peaks come from the web download at first play, so the Loops list, the loop builder preview, and the library show the flat band for a file until it has played once. Options: analyze a file when the loop builder opens on it (this needs the cached download in 8.37 to avoid a second fetch), or a low-priority background pass over saved tracks on Wi-Fi. Decide with 8.37. In the 3.4 editor this is the first thing a user sees: the waveform is a flat band until the file has played once, after which it draws (the first preview fills it in).
- [ ] 1.3 Decide the offline model with the user (decided 2026-10-26: both automatic LRU and explicit `Keep offline`; sign-out asks keep-or-clear; budget, UI states and placement proposed in `design.md`, still to confirm): automatic (recently played) versus an explicit `Keep offline` action, the storage budget, what the UI shows for a file that is or is not available offline, and what happens to cached private audio when the user signs out of Drive.
- [ ] 1.4 Native storage: confirm where downloaded audio lives on iOS and Android (file system, not AsyncStorage) and whether `react-native-track-player` can play from local files with the same transport and lock-screen behavior.
- [ ] 1.5 Sheet music offline (moved here on 2026-10-19 from `lyrics-lookup-and-saving` 15.2, at the user's direction). A track's opened sheet music (a Drive PDF, MusicXML or MIDI file, or a linked page) should follow whatever offline model 1.3 decides for audio: the same automatic-versus-`Keep offline` choice, the same budget and sign-out handling for private Drive files, and an offline state in the viewer's source switcher. Linked pages (MuseScore, other websites) cannot be cached and should say so. Score files are small next to audio, so check whether they can be kept with the track rather than in the audio LRU. Decide with 1.3.
- [ ] 1.6 **Offline files view** (user, 2026-10-26). A dedicated view opened from the user-icon session menu (`drive-session-menu`) listing every offline file with clear sizes, total used against the budget, kept/automatic badge, sort by size, and removal of one file, a selection, the automatic cache, or everything. Reuse the library file rows and the multi-selection flow; share one size formatter with the download progress label. Explore the layout and which components to reuse with the user before building. Covered by the "dedicated view" requirement in `specs/offline-audio-caching/spec.md`; builds after the store exists (1.1, 1.4).
- [ ] 1.7 (found during 1.1(c); address after the planned tasks) **A player download that joins a background waveform download shows no progress.** A shared download publishes progress to the store of whichever caller started it. If the prefetch starts it, the mini-player's loading/slow state stays idle for a player waiting on that download. Options: publish to every waiter's store, or have the player's store take over when a player waiter joins.
