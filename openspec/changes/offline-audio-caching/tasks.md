## 1. Offline audio caching

Moved here on 2026-10-12 from `nocturne-visual-system-and-playback-shaping` (items 8.37 and 8.43), at the user's direction, so that change could be completed and archived. Scope widened by the user from a replay cache to long-term offline playback. Nothing here is scheduled: write the design and spec deltas first.

- [ ] 1.1 (was 8.37) **Playing the same file again always downloads it again; there is no cache (improvement).** Answers "isn't it already in cache?" (user, 2026-09-30): no. On web every `add()` fetches the whole Drive `alt=media` response into a fresh blob (`saved-track-web-download.ts`), and the next `reset()` / `stop()` revokes it (`saved-track-player-web-load.ts`). Measured in the preview on 2026-09-30: each press of `Preview` in the loop builder, a new range (a new `loop-preview:<source>:<start>:<end>` item id), a track or loop of the same file, and every 8.35 reload is a full download of the same 3.4–8 MB (2–28 s depending on the connection). Plan: (a) a size-capped LRU of downloaded blobs keyed by `driveFileId` + Drive content version (`modifiedTime`, matching 4.2's peak cache key), kept in memory and optionally in Cache Storage or IndexedDB so a reload is warm, with `reset()` releasing the player's hold rather than revoking a cached blob; (b) concurrent requests for one file share one in-flight download; (c) 4.1's decode for waveform peaks reads the same cached bytes instead of fetching again; (d) check what react-native-track-player does natively (it streams the URL with headers, so repeated starts may already re-buffer) before deciding whether the cache is web-only; (e) cover key/version invalidation, LRU eviction, the shared in-flight download, and abort-on-supersede (8.33: a superseded request must not cancel a download another waiter still needs) in `saved-track-web-download.spec.ts`.
- [ ] 1.2 (was 8.43) **Files that were never played have no waveform.** Peaks come from the web download at first play, so the Loops list, the loop builder preview, and the library show the flat band for a file until it has played once. Options: analyze a file when the loop builder opens on it (this needs the cached download in 8.37 to avoid a second fetch), or a low-priority background pass over saved tracks on Wi-Fi. Decide with 8.37. In the 3.4 editor this is the first thing a user sees: the waveform is a flat band until the file has played once, after which it draws (the first preview fills it in).
- [ ] 1.3 Decide the offline model with the user: automatic (recently played) versus an explicit `Keep offline` action, the storage budget, what the UI shows for a file that is or is not available offline, and what happens to cached private audio when the user signs out of Drive.
- [ ] 1.4 Native storage: confirm where downloaded audio lives on iOS and Android (file system, not AsyncStorage) and whether `react-native-track-player` can play from local files with the same transport and lock-screen behavior.
- [ ] 1.5 Sheet music offline (moved here on 2026-10-19 from `lyrics-lookup-and-saving` 15.2, at the user's direction). A track's opened sheet music (a Drive PDF, MusicXML or MIDI file, or a linked page) should follow whatever offline model 1.3 decides for audio: the same automatic-versus-`Keep offline` choice, the same budget and sign-out handling for private Drive files, and an offline state in the viewer's source switcher. Linked pages (MuseScore, other websites) cannot be cached and should say so. Score files are small next to audio, so check whether they can be kept with the track rather than in the audio LRU. Decide with 1.3.
