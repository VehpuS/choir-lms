## 1. Offline audio caching

Moved here on 2026-10-12 from `nocturne-visual-system-and-playback-shaping` (items 8.37 and 8.43), at the user's direction, so that change could be completed and archived. Scope widened by the user from a replay cache to long-term offline playback. Nothing here is scheduled: write the design and spec deltas first.

- [x] 1.1 (was 8.37) **Progress 2026-10-26: (a) in-memory LRU, (b), and (e) are done on web** (`saved-track-audio-cache.ts`, shared in-flight with waiter counting in `saved-track-web-download.ts`, keyed by `driveFileId` + `modifiedTime`, 200 MB budget; downloads without a version are never reused). **(c) done 2026-10-27: the waveform prefetch downloads through the shared download (cache hit or joins the player's), opting out of reset cancellation.** **(a) persistence done 2026-10-27 on web: `playback/audio-cache/` (an `AudioStore` interface, an IndexedDB store, a versioned LRU over it; native uses a no-op store until 1.4); a reload reads the persisted file inside the shared download. Verified in the browser preview 2026-10-27: first play wrote a 4.7 MB entry; after a reload the track played with no `alt=media` request, and with the store cleared the same play made one.** (d) the native check moved to `native-playback-follow-ups` 1.10 on 2026-10-27 at the user's direction; this change is web only, with native tracked there. **Playing the same file again always downloads it again; there is no cache (improvement).** Answers "isn't it already in cache?" (user, 2026-09-30): no. On web every `add()` fetches the whole Drive `alt=media` response into a fresh blob (`saved-track-web-download.ts`), and the next `reset()` / `stop()` revokes it (`saved-track-player-web-load.ts`). Measured in the preview on 2026-09-30: each press of `Preview` in the loop builder, a new range (a new `loop-preview:<source>:<start>:<end>` item id), a track or loop of the same file, and every 8.35 reload is a full download of the same 3.4–8 MB (2–28 s depending on the connection). Plan: (a) a size-capped LRU of downloaded blobs keyed by `driveFileId` + Drive content version (`modifiedTime`, matching 4.2's peak cache key), kept in memory and optionally in Cache Storage or IndexedDB so a reload is warm, with `reset()` releasing the player's hold rather than revoking a cached blob; (b) concurrent requests for one file share one in-flight download; (c) 4.1's decode for waveform peaks reads the same cached bytes instead of fetching again; (d) check what react-native-track-player does natively (it streams the URL with headers, so repeated starts may already re-buffer) before deciding whether the cache is web-only; (e) cover key/version invalidation, LRU eviction, the shared in-flight download, and abort-on-supersede (8.33: a superseded request must not cancel a download another waiter still needs) in `saved-track-web-download.spec.ts`.
