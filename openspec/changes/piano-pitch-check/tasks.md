## 9. Future work

- [ ] 9.1 Replace the synthesized `Piano` with recorded samples. Find a set whose licence allows bundling (CC0 or equivalent; CC-BY with attribution in Settings would also work if the user agrees), about one sample every minor third from C2 to C7 compressed to ≤ 1.5 MB, loaded lazily on first press behind `PianoVoice`. Restore the first-press queue (1.5 s cap), the load-failure fallback to the organ with a quiet notice, and their specs. Confirm the licence choice with the user first.
- [ ] 9.2 (UX, explore with a user before building) **Keyboard scrolling.** Scrolling is the minimap beneath the keys (a touch seeks the window) or a horizontal wheel/trackpad gesture on the keys; there is no momentum drag and no pinch-to-zoom key width (the latter is out of scope in the proposal). Ask singers whether the minimap is discoverable, whether they expect to drag the keys themselves, and whether the 28 pt strip is a comfortable target; consider a grab-and-fling on the strip, octave jump buttons, or a "centre on my part" control.
- [ ] 9.3 (UX, explore with a user before building) **Tapping notes while reading.** A touch that begins on a notehead plays it, including when the same touch turns into a scroll of the score (the pointer-cancel then releases it), and a tap also shows the staff's part name (the existing part peek). Ask whether notes should sound only on a still tap or after a press-and-hold, whether the part peek and the note should both fire, and whether a first tap should select a note (highlight, show its name) before a second plays it.
- [ ] 9.4 (UX, explore with a user before building) **Piano control placement on the playback screen.** The spec places it in the transport area; it was built as a fifth tile in the practice row (beside Speed, Pitch, Repeat, and Queue mode) so the five-button transport row stays uncrowded. Check with users that they look for it there, and whether the practice row is too full on a small phone.
- [ ] 9.5 (UX, explore with a user before building) **Note feedback and learning aids.** Beyond the key labels, consider showing the tapped note's name (with the sounding octave) near the notehead or on the handle row, a "hold to sing" tuner readout, or an option to keep the last tapped key lit; and whether `Black key names` should follow the score's key signature instead of a fixed sharps/flats choice.
- [ ] 9.6 (accessibility, not built) Keys and tappable noteheads have no screen-reader mapping and no computer-keyboard play mapping (both out of scope in the proposal). Decide whether the keys need an accessible alternative (for example a list of notes to activate) and add it with the computer-keyboard mapping.
- [ ] 9.7 (verify in 7.1, then record here if wrong) **Chord noteheads.** OpenSheetMusicDisplay's `getNoteheadSVGs()` is documented as returning "the paths of a chord's heads"; `tagScoreNoteheads` tags every element it returns with that graphical note's pitch. Confirm in the browser that a chord's heads each get their own pitch; if the library returns all heads for every note of the chord, assign them by order (lowest head to lowest pitch).
- [ ] 9.8 (out of scope, found while verifying) **Unhandled `NotAllowedError: Wake Lock permission request denied` in the sheet music viewer on web.** `useKeepAwake` (expo-keep-awake) rejects when the browser pane denies the screen wake lock, surfacing as an uncaught promise rejection in the console each time the viewer opens. It is harmless to the viewer, but it is noise in the console and may be reported as an error by monitoring. Catch and ignore the rejection where the hook is used, or guard it behind a feature check.
