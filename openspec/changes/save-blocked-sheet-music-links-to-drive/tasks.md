## 6. PDF zoom

- [x] 6.1 **Check what PDF zoom does today** on web with a real Drive PDF (the `Radio Video V5.0 Score and Parts` PDF is a good one): the − and + buttons (50% to 400%, `pdf-page-layout.ts`), whether the zoom value reads correctly, whether the page stays sharp at 300% and 400%, and whether scroll position is kept when zooming. Record what is missing or broken here and in `design.md` before changing anything; adjust 6.2 to match. _Measured 2026-10-23; full findings in `design.md` Decision 8. Summary: the real PDF has 81 pages; the buttons stop at 300%, not 400% (viewer cap 3, layout cap 4); no gesture handlers exist; zoom drifts the point under the viewport centre; canvases are sharp to 300% on a phone but fall to 0.85x at 300% on a 1200 px window; memory is flat and rapid steps settle in about 0.5 s. Whether to reach 400% is an open question for the owner (design Open Questions); 6.2 to 6.4 below are adjusted to 300% until it is answered._
- [x] 6.2 Add direct-manipulation zoom for PDFs on web: pinch on a touch screen, `Ctrl`/`Cmd` + wheel or trackpad pinch on desktop, and double-tap or double-click to toggle between fit-to-width and a readable zoom (about 200%). Keep the point under the fingers fixed while zooming, clamp to the existing range, and keep the toolbar value in step. Put the gesture-to-zoom math in a pure model (`pdf-zoom-gestures.ts`) with a spec for focal-point scroll offsets, clamping, and the double-tap toggle; keep DOM listeners thin and `.web` only. _Done. The PDF maximum is 400% (owner's decision); scores stay at 300%. Pure math in `viewer/pdf-zoom-gestures.ts`; thin DOM listeners in `viewer/attach-pdf-zoom-gestures.web.ts` (wheel with `Ctrl`/`Cmd`, two-finger pinch, Safari gesture events, double tap and double click, `touch-action: pan-x pan-y`, one zoom per animation frame). The viewer's zoom state has a new `set` action so the toolbar follows gestures, and the toolbar's `+` disables at the document's own maximum. A first live check with synthetic events showed the handlers attach, `Ctrl`+wheel is prevented and holds the focal point exactly, and `+` disables at 400%; real touch is for 6.4. Measured for 6.3: with the pages at 400%, a double click back to 100% held the main thread for about a second before the readout updated._
- [x] 6.3 Make sure repeated zoom steps do not queue a full re-render of every page: coalesce rapid changes so only the final zoom renders at full resolution (a CSS scale in the meantime), and release canvases for pages far from the viewport at high zoom. ## 8. Future tasks (found during this change, not done here)

- [x] 8.1 **Explore with a user before changing:** PDF pages go soft above about 250% on wide windows (a 1200 px pane draws 0.85x at 300%) because of the 12-million-pixel canvas cap in `pdf-page-layout.ts`. Decide whether sharper zoom is worth drawing only the visible part of a page, and whether the maximum should rise to 400%, then act. Measurements are in design Decision 8. _Closed 2026-10-26 by the owner as no action needed (leave it). A canvas is capped at 12 million pixels, so on an A4-shaped page a 1200 px window draws about 2.0 canvas pixels per CSS pixel at 100%, 1.3 at 200%, 0.85 at 300% and 0.64 at 400%; a 390 px phone stays near 1.9 at 400%. This matches the pdf.js viewer. Alternatives not taken: draw only the visible part of each zoomed page (sharp everywhere, about a day of work across all three layouts), raise the cap to about 16 million (little gain, Safari memory risk), or lower the maximum zoom on wide windows. Revisit if desktop users report soft text._
- [x] 8.2 **Explore with a user before changing:** the Save to Drive flow is web only. Decide how native iOS and Android should choose a file (document picker) and request the write scope; this extends `native-playback-follow-ups` (task 7.4 below records the entry). _Closed 2026-10-26 by the owner as explored and deferred to `native-playback-follow-ups` 1.9. Findings: native has no CORS, so the `blocked` card that triggers Save to Drive on web should rarely appear on a phone (only HTML-page links, offline, or unreachable); the write scope is already requested on every platform by `use-authorization.ts`, but not tested on a device; the missing piece is a native `chooseDeviceFile` (for example `expo-document-picker`, a new dependency and dev-client rebuild) plus removing the `Platform.OS === 'web'` gate in `sheet-music-host.tsx`, and a device check of the folder picker and progress/cancel. Option left for later: build only `From this device` natively._
- [x] 8.3 **Explore with a user before changing:** the Save to Drive sheet stacks over the manager sheet (two sheets on screen during the transition). Check on a phone whether replacing the manager's content instead would feel calmer. _Closed 2026-10-26 by the owner as no action needed (leave it stacked). The manager stays mounted and `Save to Drive` opens as a second modal over it (double scrim, manager rim visible), the same as the Drive picker; within the save flow the folder step already replaces the save sheet. Not taken: hiding the manager while the save sheet is open (about 5 lines, and the Drive picker would want the same for consistency), or folding the save steps into the manager sheet (bigger, and the viewer still needs the stacked sheet). Not checked on a phone; revisit if the doubled scrim bothers anyone._
- [x] 8.4 **Explore with a user before changing:** pdf.js draws on the main thread (the "fake worker"), so a dense page is likely what blocks the UI for up to about a second (not profiled; seen on zoom out from 400% to 100% on the 81-page score: three canvas swaps over 1.4 s, the last at 1.36 s). Decide whether to serve a real pdf.js worker (static file at a known path, or a bundled worker) and whether to show a progress hint while a page draws. Measurements are in the 6.3 note. _Profiled 2026-10-26 in the web preview on the 81-page Drive score (phone-width pane and a 1200 px window; long-task observer, rAF gaps, and timed canvas calls): no long task over 50 ms and no frame gap over 41 ms in any of: 100% to 400% and back by `Ctrl`+wheel stream, double click from 400% to 100%, and first draws of never-seen pages across the document. Each page finished drawing within about 50 ms of scrolling to it; 2D-context paint calls totalled 1 to 5 ms per burst, so the time is pdf.js JavaScript, split into small slices. The earlier 1 s gap did not reproduce, so it was probably a cold or throttled run. A real worker is not justified by this; revisit only if a dense score reproduces a stall on a low-end phone. Closed 2026-10-26 by the owner as no action needed (no worker, no progress hint)._
