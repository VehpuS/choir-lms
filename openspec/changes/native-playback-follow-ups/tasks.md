## 1. Native playback follow-ups

Moved here on 2026-10-12 from `nocturne-visual-system-and-playback-shaping` (group 8), so that change could be completed and archived. Web is the verification target for that change; these three items need a native decision or a device. Nothing here is scheduled: pick them up when native becomes a priority target, and write the design and spec deltas first.

- [ ] 1.1 (was 8.41) **Native waveform peaks (deferred by the user 2026-10-06 until native is prioritized as a target; see the native note under group 7).** Native shows the flat placeholder band for every item because it has no decoder (4.1). Options, from the 4.1 measurements: (a) a native decoder module such as `react-native-audio-api` (`decodeAudioData` on a downloaded file; needs a dev-client rebuild and a file download step, and its Expo 54 / RN 0.81 compatibility must be confirmed, which the sandbox could not check); (b) a JS-only partial MP3 decode that skips the expensive synthesis stage: walk frames, Huffman-decode and requantize the spectral coefficients, and take energy per granule as the envelope (the user's JS preference; MP3 only, and m4a / AAC, FLAC, and Ogg would stay flat); (c) extracting on the server, which does not exist. Needs a spike on (b)'s speed in Hermes before committing, and the user's decision on (a) versus (b).
- [ ] 1.2 (was 8.51) **Semitone pitch on native iOS and Android (deferred, deliberately not planned; reconfirmed by the user 2026-10-06).** Decided by the user (2026-10-02): web is the priority platform, so native pitch is skipped in this change and is implemented only if native becomes a priority; no task here should build toward it. What must hold meanwhile: the limitation is explicit in code (`canShapePitch`, 5.1) and the native UI shows the inert fallback with its reason (6.1, spec `playback-shaping`). If revived, options and costs are recorded under 5.0: Android needs RNTP to expose ExoPlayer pitch (patch or fork; no `patch-package` setup and no Android project directory today), iOS needs an `MTAudioProcessingTap` + SoundTouch or an `AVAudioEngine` / `AVAudioUnitTimePitch` module (the latter needs the file on disk, overlapping 8.37); both need on-device verification. Native pitch detection (1.12) shows the score's track-pitch offset once this exists; until then it is zero on native.
- [ ] 1.3 (was 8.44) **Peak storage budgets and eviction are untested on device (verify).** Web IndexedDB is budgeted at 64 MB (about 500 five-minute tracks) and native AsyncStorage at 3 MB (about 25); Android's database cap, per-row size limits, and iOS behavior were not exercised because native has no extractor yet. Re-check when 8.41 lands, including what happens at quota errors (today a failed write is swallowed and the peaks stay in memory only).
- [ ] 1.4 (was 8.98) **Verify the menu icons on iOS and Android (manual).** Check the icon alignment, tint, vertical centering, and 50pt rows of the options menus and pickers (shared icon map in `library/components/options-menu-sheet/menu-action-icons.ts`); only the web preview was checked.
- [ ] 1.5 (from `lyrics-lookup-and-saving` 7.1) **Native verification of lyrics on iOS and Android (manual).** Check the lyrics editor sheet (keyboard handling with the multiline field and `Save` still reachable, text selection, safe areas), the mini-player `Show lyrics` control and half-height peek, and full-screen reading mode (selectable text, the text-size control, the close and play/pause controls, safe areas, and that `expo-keep-awake` keeps the screen on while reading mode is open and releases it on close). Also confirm `Search the web` opens the system browser and that the lookup disclosure appears once. **Update (2026-10-19, from `lyrics-lookup-and-saving` 8.5):** keyboard avoidance for every sheet and dialog was added for iOS and checked on the iOS simulator (lyrics editor, Settings forms, centered dialog). **Still to check on Android:** whether `Modal` sheets resize or sit under the keyboard (Android version, edge-to-edge, `softwareKeyboardLayoutMode`), the lyrics editor and every sheet with a text field, and a physical iPhone and Android phone for the multiline field's caret scrolling.
- [ ] 1.6 (from `lyrics-lookup-and-saving` 15.1, planned 2026-10-14) **Native sheet music viewer on iOS and Android (implement and verify).** The sheet music change builds the shared model and the web renderers only; native implementation is bundled here by the user's decision (2026-10-14), not built there. Native needs the `SheetMusicRenderer` implementations (a WebView host for OpenSheetMusicDisplay and pdf.js, or a native PDF view; the options and Expo SDK 54 compatibility are recorded by that change's spike 9.2), the Drive and URL loaders running on device, and a manual check of the full-screen viewer (zoom and pan gestures, part chips, source switcher, safe areas, keep-awake, memory on a long PDF, and the manager sheet and Drive picker). Until then a native build lists sources and opens them outside the app. Score marks for pitch detection (1.12) and the `Show other-octave matches` toolbar toggle need this viewer.
- [ ] 1.7 (from `piano-pitch-check` 8.2) **Piano sound on native iOS and Android (spike, then implement and verify on device).** The piano overlay and tappable score notes are web-only: `pianoCapabilities().canPlay` is false on native, so the controls are absent there. Native needs bundled-sample (or synthesized) audio that mixes over `react-native-track-player` without taking its audio focus or ducking it, with low enough latency for a held key. Spike first to choose a dependency (for example `react-native-audio-api`, which also appears under 1.1(a), or an `expo-audio` player pool), check its Expo SDK 54 / RN 0.81 compatibility, and measure first-press latency and polyphony on a device. The model layer is already shared (`PianoVoice`, the key gesture model, the sound engine, the notehead tap hook is web DOM only), so native needs a voice, a native keyboard pointer surface, and, with 1.6, native score note taps. On Android check audio focus (the piano must not pause the track); on iOS check the silent switch and the audio session category. The detected-key state and edge pill for pitch detection (1.12) need this keyboard.
- [ ] 1.8 (out of scope, found 2026-10-20 while reloading the iOS app) **`react-native-track-player` JS and native module are out of step in the installed iOS dev build.** Metro logs warnings that the Objective-C signatures for `getSleepTimerProgress`, `setSleepTimer`, `sleepWhenActiveTrackReachesEnd`, and `clearSleepTimer` are missing from `TrackPlayerModule`, so those JS methods are unavailable. The app does not use the sleep timer today, so playback is unaffected, but it means the installed development build was made before the current `react-native-track-player` version. Rebuild the dev client (`expo run:ios`) after the dependency bump, confirm the warnings go away, and check whether the Android build has the same mismatch. Also note `SafeAreaView has been deprecated` is logged on iOS (the shell uses `SafeAreaView` from `react-native`); move to `react-native-safe-area-context` when native becomes a priority.
- [ ] 1.9 (from `save-blocked-sheet-music-links-to-drive` 7.4, 8.2) **`Save to Drive` on native iOS and Android (explore with a user, then implement and verify on device).** The save flow is web only: `choose-device-file.ts` returns `unsupported` on native and the blocked card, row menu, and `Add sheet music` offer `Save to Drive` and `From this device` only when `Platform.OS === 'web'`. Native needs a document picker (for example `expo-document-picker`, which reads the file Safari or Chrome downloaded to Files or Downloads), the `drive.file` scope requested through the native sign-in and checked with `hasDriveWriteScope`, the same content check and 25 MB limit, and a device check of the folder picker sheet and progress/cancel. Decide with a user how the "download in the browser, then choose the file" steps read on a phone before building. Explored 2026-10-26: native has no CORS, so the blocked-link trigger rarely applies; the smallest useful slice is `From this device` alone (picker plus removing the web gate), and the write scope is already requested on every platform but untested on a device.
- [ ] 1.10 (from `offline-audio-caching` 1.1(d), 1.4 and the native half of 1.3, moved 2026-10-27) **Native offline audio storage (spike, then implement and verify on device).** Web persists downloaded audio in IndexedDB behind the `AudioStore` interface (`playback/audio-cache/`); native uses a no-op `audio-store.ts` so every read misses. Steps: (a) check what `react-native-track-player` does natively on repeated starts (it streams the URL with headers, so each start may re-buffer) before deciding how much a cache gains there; (b) confirm where downloaded audio should live on iOS and Android (file system via `expo-file-system`, a new direct dependency present transitively in the lockfile, with the index in AsyncStorage; not AsyncStorage for bytes) and whether `react-native-track-player` plays a `file://` URL with the same transport and lock-screen behavior; (c) implement the native `AudioStore`, the shared in-flight download and the Drive-version invalidation on native, with the same budget (500 MB default, user-set size), `Keep offline` pin and LRU rules as web; (d) check the storage and quota behavior on device. Follows the offline model in `offline-audio-caching` design.md and its spec.
- [ ] 1.11 (from `offline-audio-caching` 1.2, 1.3, 1.5 and 1.6, moved 2026-10-27) **Native offline UX and score files (verify and implement on device).** After 1.10: the sign-out keep-or-clear prompt, the offline files view with sizes and the cache size control, per-file offline states, and offline opened sheet music (score files stored on the file system with the track's pin state) on iOS and Android; playing a cached file with no network and no Drive session. Native has no waveform decoder (1.1 here), so never-played files stay a flat band on native until that is decided; the cached bytes make a later native extractor cheap to feed.
- [ ] 1.12 (from `pitch-detection` 7.1) **Native pitch detection on iOS and Android (spike, then implement and verify on device).** Pitch detection is web-only: `pitchCapabilities().canListen` is false on native and `pcm-source.ts` (native) fails closed, so every pitch control is absent there. The shared pieces are done and tested (`@org/pitch-detection`, `PitchStore`, the monitor strip, the Pitch view, the `Minimum volume` meter, the piano detected state, score marks); native needs:
  - (a) **Capture-library spike.** `react-native-audio-api` (`AudioRecorder.onAudioReady`, float buffers, MIT, FFmpeg only if `enableFFmpeg`) versus `@siteed/audio-studio` (`startRecording` with `streamFormat: 'float32'`, MIT, dev-build and plugin needs unverified). The research and licence notes are in `pitch-detection` design.md, "Native microphone capture"; decide by the checks below. `react-native-audio-api` also appears under 1.1(a) and 1.7, so one dependency could serve all three.
  - (b) **`PcmSource.native`** with the same contract as web (several subscribers over one shared stream, frames with a capture timestamp, unprocessed audio: no echo cancellation, noise suppression or auto gain), reporting `canListen` true only where capture works. The existing capability, fan-out and visibility specs are the model.
  - (c) **Permission and config:** the iOS microphone usage string, `android.permission.RECORD_AUDIO`, and the Expo config plugin options; ask only on the first `Listen`, after the explanation, as on web.
  - (d) **Coexistence with `react-native-track-player`:** the iOS audio session category and route, Android audio focus, and lock-screen controls must keep working while a track plays and capture runs; capture must not pause or duck the track.
  - (e) **Foreground only:** listen only while the app is visible (`app-visibility.ts` already follows `AppState`), with no background mode or foreground service.
  - (f) **Device checks:** buffer size, latency (web target is under 100 ms from sound to display) and CPU; the headphones hint and how much track bleed reaches the microphone; the `Minimum volume` range and default against real phone microphones (the -60 to -20 dB range was tuned in a browser); and the interruption (call, Siri) and permission-denied paths, including the `Microphone blocked` state with its settings link.
  - Depends on, for the full experience: 1.2 (native semitone pitch, so the score's `Following track pitch ±N st` offset can be non-zero; until then it is zero), 1.6 (native sheet music viewer, for score marks and the other-octave toggle) and 1.7 (native piano, for the detected key state). The monitor strip, the Pitch view and the Settings page work without them.
